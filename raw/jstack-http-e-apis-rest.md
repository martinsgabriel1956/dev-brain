# HTTP e APIs REST

Durante o curso, todas as aplicações de back-end que a gente vai desenvolver vão ser APIs REST, exatamente esse que é o tema dessa aula.

## O que é uma API

Então vamos começar entendendo primeiro o que é uma API, que é um acrônimo para Application Programming Interface. Eu vou te explicar aqui o conceito de API voltado mais para web, beleza?

Basicamente, uma API permite que a gente conecte várias aplicações de diferentes tipos em uma mesma fonte de dados. Então, vamos imaginar que a gente tenha um front-end web, um aplicativo mobile, uma outra aplicação desktop e até mesmo uma outra API. E a gente quer que todas essas aplicações consumam a mesma fonte de dados, ou seja, acessem o mesmo banco de dados, compartilhem os usuários da aplicação e tudo mais. Então, para isso acontecer, a gente precisa de alguém ali no meio e é exatamente aí que entra a nossa API.

E durante o curso, todas as APIs que a gente vai desenvolver vão ser escritas em Node.js. Então, aqui a gente já consegue identificar que elas são aplicações de back-end, então APIs executam do lado do servidor. E aí a gente vai consumir essas APIs usando aplicações web escritas em React e mobile escritas em React Native. E esse consumo, que é basicamente se conectar essas aplicações à nossa API, elas vão ser feitas através de HTTP, requisições HTTP. E é exatamente disso que a gente vai falar agora.

## O protocolo HTTP

Vamos entender um pouquinho mais sobre como é que funciona o protocolo HTTP. Bom, o protocolo HTTP é basicamente uma troca de mensagens entre duas pontas. Então, do lado esquerdo a gente tem o cliente, que a gente pode ter lá um aplicativo mobile, uma aplicação web, um aplicativo desktop, enfim, literalmente qualquer tipo de programa ou dispositivo que consiga fazer requisições HTTP. E aí a gente faz a requisição para um servidor. Então, a gente manda uma mensagem para ele falando, oi, eu quero alguma coisa. E aí o servidor responde de volta o que a gente pediu. Então, é basicamente como eu disse, uma troca de mensagens. O cliente pede e o servidor responde de volta.

Porém, obviamente, não é só isso, não é tão simples assim. E por trás dessas requests e responses acontece muita coisa. E é exatamente sobre isso que a gente vai falar a partir de agora. E eu já te adianto para você não se assustar, porque agora vai vir muita informação em cima de você. Eu sei que é bastante coisa, que talvez fique um pouco difícil de assimilar, mas não se assusta, porque ao decorrer aqui da aula eu vou te dar exemplos, eu vou destrinchar um pouquinho melhor cada tópico. E outra coisa, quando a gente for para a prática, as coisas vão ficar muito mais claras e as peças vão começar a se encaixar. Então, vamos lá.

## A request

Uma requisição é basicamente formada por alguns blocos de informações. Então, a gente tem a nossa URL, o endpoint, a gente tem os query params, temos os métodos, temos os headers e também temos o body. A URL e o endpoint servem para a gente conseguir identificar os recursos. Os query params são parâmetros adicionais que a gente passa na URL. Os métodos são para a gente identificar qual ação a gente quer tomar em cima do recurso que a gente identificou com a URL e o endpoint. Os headers são para a gente conseguir trocar informações adicionais entre cliente e servidor. E o body serve basicamente para a gente mandar qual é o corpo da nossa mensagem.

Agora, vamos entender um pouquinho mais a fundo cada um desses tópicos. Então, começando aqui pela URL, endpoint e query params. Como eu disse, a URL e o endpoint servem para a gente conseguir identificar os recursos. Então, por exemplo, a gente acessaria lá no navegador https://mywebsite.com, isso é a nossa URL, barra products, tudo que vem depois do nosso domínio, do .com.br. Então, barra alguma coisa, esse barra alguma coisa é o nosso endpoint. É onde a gente identifica qual é o recurso que a gente está tentando acessar. Onde a gente fala para o back-end qual é o recurso que a gente está tentando acessar. Então, nesse caso, por exemplo, eu estou tentando visualizar uma listagem de produtos, então o endpoint é barra products. E aí os query params é para a gente passar algumas informações adicionais. Então, eu estou dizendo o seguinte, olha, back-end, eu quero listar todos os produtos, só que eu quero que você me traga os produtos da página 3 e ordenados pelo nome.

Partindo agora para os métodos, como eu já disse, eles servem para a gente identificar qual ação a gente está tentando tomar em cima do recurso que a gente identificou lá no nosso endpoint. Existem alguns outros além dos que eu vou te mostrar aqui, mas esses são os principais e os que a gente precisa conhecer para começar a desenvolver as nossas APIs. Bom, então quando a gente acessa lá no browser a URL que eu mostrei no slide anterior, a gente está fazendo uma requisição do tipo GET e requisições do tipo GET servem para a gente consultar dados, ou seja, o back-end entende que ele precisa retornar uma lista de produtos. Agora, se a gente quisesse cadastrar um novo produto, a request devia usar o método POST, que aí sim o back-end entende que a gente está tentando inserir um novo registro. Já se a gente quisesse editar, a gente precisaria usar o método PUT e se a gente quisesse deletar um produto, a gente usaria o método DELETE.

Falando agora sobre headers, eles basicamente, como eu já falei, servem para a gente conseguir trocar informações adicionais, eu já vou te dar alguns exemplos de que tipo de informação a gente troca via header, entre cliente e servidor. Aí uma coisa legal é que a gente consegue enviar header tanto nas nossas requests quanto receber nas nossas responses, beleza? E aí, já existem alguns headers que são predefinidos pelo próprio HTTP, digamos assim, é um standard, só que a gente também consegue criar alguns headers customizados e eu já vou te mostrar ali uma boa prática para criação de header customizado e também o motivo, um exemplo de um motivo onde a gente gostaria de criar um header.

E agora, partindo para as características dos headers, eles são super simples, são basicamente compostos de chave e valor separados por dois pontos. Então, no exemplo ali, a gente tem um header que já é padrão do HTTP, que é o content type, então a gente tem content type, dois pontos, application barra JSON, a gente está dizendo que o nome do header é content type e o valor dele é application barra JSON. Esse content type serve para a gente identificar qual é o tipo de informação que a gente está mandando dentro da nossa request e também serve para o servidor mandar para o cliente, para quem está fazendo a request, qual é o tipo de mensagem que ele está enviando dentro do corpo da resposta.

E uma outra característica é que os headers são case-insensitive, ou seja, tanto faz se o nome do header está em maiúsculo, se está em minúsculo, não importa, ele vai funcionar da mesma forma, então ali a gente tem o content type todo em minúsculo e eu também já aproveitei para colocar o authorization, que é um header que a gente vai usar mais para frente para enviar, por exemplo, o token JWT de autenticação do usuário. Então, aí já está um exemplo, uma das informações que a gente envia dentro do nosso header são tokens de autenticação.

E aí, para criar um header customizado, uma boa prática é sempre a gente colocar um X na frente para identificar que aquele header é um header da nossa aplicação. E agora um exemplo de por que a gente gostaria de criar um header customizado. Vamos imaginar que a gente tem uma aplicação onde o usuário pode ter múltiplas organizações e aí a gente quer identificar, sempre que a gente, por exemplo, vai fazer uma ação, vai cadastrar um usuário, saber dentro de qual organização a gente está tentando cadastrar aquele usuário. E aí a gente coloca essa informação, por exemplo, dentro do header X-Org-ID, e aí sempre que o usuário trocar lá dentro da nossa interface qual é a aplicação, qual é a organização que ele está selecionado, a gente troca esse header para assumir o ID dessa organização que ele selecionou.

E agora, para finalizar a parte de request, a última coisa que está faltando a gente falar sobre é o nosso body. E o body, a primeira coisa que a gente precisa saber, então, é que ele só está presente em requisições do método post e put, tá? Nas outras, a gente não envia body.

E o formato dos dados que a gente envia dentro desse body normalmente vão ser no formato JSON, que é o JavaScript Object Notation. Esse formato é bem poderoso, primeiro porque praticamente qualquer linguagem de programação hoje em dia consegue ler ele, e segundo que a gente manda praticamente qualquer tipo de dado aqui dentro. Então a gente consegue enviar string, array, objetos aninhados, números, enfim, é bem legal esse carinha, porém tem um tipo de dado que a gente não consegue enviar aqui dentro que são arquivos binários, então imagens, PDFs, áudios, vídeos, todo esse tipo de arquivo a gente não consegue enviar dentro do JSON.

A gente até consegue, fazendo uma gambiarrinha ali, que é converter para Base64, e aí mandar dentro do JSON no formato string, só que isso aí acaba pesando mais a nossa requisição, em alguns casos nem conseguimos fazer isso. E aí para enviar esses tipos de arquivos, a gente não usa o formato JSON, a gente usa um outro tipo de requisição, aliás, de corpo, que é o multipart/form-data, tá? E aí dentro dele sim a gente consegue enviar arquivos binários, texto, string, número, qualquer outro tipo de dado, assim como a gente enviava dentro do JSON, tá? E aí o multipart/form-data também é bem simples, ele é basicamente composto por chave e valor.

## A response

Partindo agora para as responses, assim como as requests, elas também são formadas por alguns bloquinhos de informação, então a gente tem os headers, o Content Type, o Status Code e o body, tem mais algumas coisas, né? Lógico, mas isso daqui são as principais que a gente precisa conhecer. Os headers a gente já viu, então serve para a gente trocar informação adicional. O Content Type é para a gente identificar, né? Para mandar ali dentro do header, qual que é o tipo de conteúdo que a gente está enviando dentro do corpo da nossa resposta.

E aí a gente também tem um outro header, que é o Status Code. O Status Code serve para a gente indicar para o servidor, indicar para quem está fazendo a requisição, para o nosso cliente, qual que é o proceder daquela request, né? Ou seja, o que aconteceu com ela? Deu certo? Deu errado? Se deu errado, foi um erro de autorização? Foi um erro no servidor? Enfim, o que aconteceu? E aí a gente tem, obviamente, o body, que são os dados que o cliente, que quem fez a request pediu para o servidor.

Vamos ver agora só um pouquinho bem rápido desses Status Code, né? Porque o resto a gente já viu tudo. Então, os Status Codes são separados por categoria e o que indica a categoria é o primeiro dígito. Então, códigos de 100 a 199, por exemplo, são respostas de informação, 200 a 299, respostas de sucesso e tudo mais. O que mais interessa para a gente são os códigos com o dígito 2, 4 e 5. E mais especificamente, esses aqui da direita. Então, 200, 201, 400. Um que você provavelmente já viu muito por aí, que é o 404, né? Que é o de Not Found, quando a gente não encontra o recurso, quando a gente não encontra a página, enfim. Então, esses códigos aí são os que a gente vai estar usando durante o curso. ## Exemplo de request e response

E aí, dentro dos headers dessa requisição, a gente teria lá o nosso path com barra products, que é basicamente ali o nosso Endpoint, ou seja, tudo que vem depois do nosso domínio.

O método que, como eu já expliquei também, toda vez que a gente acessa uma URL de dentro do nosso navegador, usando o nosso browser, essas requisições elas são do tipo GET, não tem como fazer outro tipo de requisição, tá? ## O padrão REST

Então agora só para concluir essa aula, que eu sei que já foi bastante conteúdo, foi muita informação, eu vou te explicar o funcionamento do padrão REST. E olha só que interessante, a gente já está em uns 12 minutos de aula e a gente nem tocou no nome do REST direito. Só que agora que você já entendeu o que é uma API, como é que funciona todo o protocolo HTTP, eu consigo te explicar o que é o REST em aproximadamente 1 ou 2 minutos. Olha só que legal.

Vamos rapidamente aqui então só relembrar o que é uma API. Uma API é basicamente uma aplicação que permite que a gente conecte várias outras aplicações de diferentes tipos e tecnologias em uma mesma fonte de dados, beleza? E agora sim a gente entra no REST. O que é o REST? O REST não passa de um padrão para construção de APIs que utiliza o protocolo HTTP. Simples assim, bem fácil, né? A grande diferença, a grande sacada dele é que ele retorna a uma representação do estado e hoje já vou te explicar isso aí.

Antes vamos dar uma olhada rápida aqui na padronização de nomes de endpoints dentro do REST. E é muito simples, é só a gente usar o nome dos recursos sempre no plural. Então se eu quiser, por exemplo, um endpoint para obter uma lista de produtos, eu faria uma requisição com o método HTTP GET para endpoint barra products. Se eu quiser, por exemplo, pegar os dados de um produto com o ID 10, eu faria uma requisição GET para endpoint barra products barra 10. Aí essa barra 10 é o que a gente chama de parâmetros. A gente vai ver tudo isso mais para frente conforme a gente for desenvolvendo as nossas aplicações e avançando no curso. E aí esse mesmo padrão se repete para o POST, para o PUT, onde a gente também informa qual que é o ID do produto que a gente está tentando editar e para o DELETE, mesma coisa, a gente informa na URL qual que é o ID do produto que a gente está tentando deletar.

## Representação do estado

E agora para a gente finalizar essa aula, vamos entender a tal da representação do estado que eu falei que a API ela retorna. Bom, alguns slides atrás eu dei um exemplo lá onde a gente fazia uma requisição no navegador endpoint barra products e ele retornava esse HTML aqui todo montadinho com os produtos dentro das LI's e tudo mais. Qual que é o problema disso aqui? Bom, vai funcionar muito bem na web, afinal de contas, o browser consegue entender código HTML. Mas e se a gente quiser usar essa mesma listagem de produtos, essa mesma fonte de dados em um aplicativo mobile, por exemplo, escrito em React Native, que não entende HTML? Como é que a gente faz?

Bom, é muito simples na verdade. Ao invés de a gente retornar esse HTML já todo montado com os produtos ali dentro, a gente retorna uma representação desses dados. Então, você pode ver que ali eu tenho os mesmos dados que eu tinha antes retornando no HTML, só que agora eu tenho eles numa estrutura que a gente chama de JSON, que inclusive a gente já viu lá no slide quando eu estava mostrando o formato que a gente manda os dados para o back-end. Então, é nesse mesmo formato que a nossa API REST ela retorna para a gente.

Poderia ser em outro formato? Poderia. Poderia, por exemplo, ser um XML. Mas o JSON hoje é o mais usado na web, no mundo inteiro, principalmente pelo fato de que praticamente, para não dizer todas as linguagens de programação, elas conseguem interpretar esse JSON, ou seja, elas conseguem ler ele, pegar as informações que estão ali dentro e aí faz o que precisa ser feito. Então, no caso da web, ela vai pegar esses dados e daí injetar dinamicamente com JavaScript ali dentro do HTML os dados que foram retornados da nossa API. Lá no mobile, mesma coisa, mas obviamente, ele vai fazer da forma que ele precisa fazer, não vai ser com LI. Então, os dados ficam acessíveis de uma forma genérica. Basta que a gente tenha uma linguagem que faça requisições HTTP para conseguir chegar no nosso servidor e depois interpretar o código JSON para montar a interface de acordo com a plataforma onde ela está rodando.
