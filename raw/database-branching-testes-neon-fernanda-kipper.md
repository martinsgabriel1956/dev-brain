# Database Branching: Como Criar Bancos de Dados de Teste Isolados por Branch

> Nota: transcrição de vídeo em fala espontânea, pontuação e quebras de parágrafo adicionadas para legibilidade. Sem tradução — fonte já em pt-BR.

Quando a gente começa a trabalhar como desenvolvedor em uma aplicação que tem clientes e tá rodando em produção, logo a gente já percebe a importância dos ambientes de teste, porque esses ambientes servem pra gente validar as nossas modificações antes de chegar no ambiente de produção. O problema é que muitas vezes a gente foca somente na branch do código e acaba esquecendo sobre o banco de dados — no final, acaba tendo um único banco de dados compartilhado por todas as branches de teste, todos os ambientes de teste, e isso acaba causando diversos problemas e muita dor de cabeça. Então nesse vídeo eu quero te mostrar uma boa prática para você criar os seus bancos de dados de teste na sua empresa e elevar o nível da arquitetura e também dos testes da sua aplicação. Então, sem mais enrolações, bora pro vídeo.

## O problema do banco de dados único

Vamos começar com o problema aqui do banco de dados único. Esse é um caso muito comum da gente encontrar dentro das empresas, que é o seguinte: a cada nova branch que a nossa equipe vai criando, que o nosso time vai desenvolvendo, com alterações, novas features, correções de bug etc., todas elas vão sendo deployadas em um ambiente de teste que compartilha um único banco de dados.

O problema é quando essa aplicação tem o controle do esquema do banco — ou seja, é uma aplicação backend, por exemplo, que tem ali o poder de rodar as migrations. Pode acontecer que em diferentes branches eu tenha alterações diferentes no esquema do meu banco, e a cada deploy eu vou fazendo as modificações nesse único banco de teste, e isso pode causar colisão de esquema, onde as migrações podem acabar se atropelando.

Por exemplo: na minha feature de login, eu fui lá e adicionei um novo campo no usuário, e mapei um novo tipo para as assinaturas — antes eu tinha só `subscription_type` de `annual` e `monthly`, e aí eu fui lá e adicionei o `semester`. Já o meu outro colega, que tá trabalhando numa feature de billing, ele tá mexendo também nessas partes de assinatura, só que ele não mexeu o esquema do banco — ele tá só cuidando de uma regra de negócio. E aí, quando ele vai testar a alteração dele nesse ambiente de testes que compartilha o mesmo banco de dados do meu ambiente de teste, ele pode acabar tendo uma série de bugs e problemas ali nos testes dele, por conta de uma alteração que eu fiz no banco — na minha atualização de esquema — que na branch dele aquela atualização ainda não existe, ou ainda não entrou em vigor.

Então começo a ter colisões de esquema, com as migrations se atropelando. Isso vai causar uma série de problemas:

- **Testes instáveis**: eu passo a não confiar mais nos meus testes, mesmo os testes manuais, porque pode ter alterações no banco de testes que não estão indo pra produção. Quando eu for levar a minha feature de login pra produção, fazer o merge, pode ser que todas as outras migrations que tinham sido aplicadas nesse banco de teste não vão junto, porque essas migrations não estão na minha branch, estão na branch dos meus colegas. Isso faz com que meu teste não seja tão confiável — nem os unitários, nem os de integração, nem os manuais — porque os ambientes não são de fato uma réplica um do outro só com as minhas alterações; é uma réplica com as minhas alterações e as alterações de todo mundo dentro do esquema desse banco.
- **Dados contaminados**: eu posso estar testando manualmente com dados que já estão contaminados com os resquícios dos testes dos meus colegas, que acabaram fazendo mudanças no esquema do banco. Isso pode acabar quebrando o meu teste também.
- **Times bloqueados**: o pior problema de todos. Eu posso ter um time que fica bloqueado esperando o outro time finalizar o teste, porque ele tá na fila para usar o banco de dados.

Mesmo tendo ambientes replicáveis de deploy — um deploy para cada branch — o problema é que o banco que essas branches utilizam, onde ficam armazenados os dados do ambiente de sandbox ou de staging, é o mesmo banco. Então eu acabo tendo os mesmos problemas que se eu tivesse compartilhando um único ambiente de teste entre todo mundo: fila para utilização do banco, necessidade de resetar o banco de dados de tempos em tempos porque aquilo vira uma bagunça, um ambiente irreproduzível que não tem nada a ver com produção (porque tem um monte de migration rolando ao mesmo tempo de várias branches diferentes), deploys mais lentos e baixa confiança no nosso setup de teste.

## A solução: database branching

É aqui que entra a solução que a gente vai falar no vídeo de hoje, que é o **database branching**. A ideia é usar branches isoladas do banco de dados pra gente conseguir evoluir esse nosso banco de testes sem levar riscos pra produção.

A moral toda é a seguinte: eu vou ter o meu ambiente de produção, que vai continuar existindo, onde eu vou ter o meu **production DB** — o banco de dados utilizado pela minha branch principal no ambiente de produção. Isso não muda. A diferença é que agora eu vou ter um novo banco de dados, que vai ser o meu banco de dados de **staging** (ou de sandbox, ou como eu queira chamar). Esse banco de staging nada mais é do que um **copy-on-write** do meu banco de dados de produção.

Isso é uma técnica de armazenamento onde eu vou ter um ambiente que na verdade compartilha os mesmos blocos dos dados originais, sem duplicar esses blocos, realizando uma cópia física somente do bloco específico que eu for alterar, no momento em que ele precisa ser alterado. Enquanto isso, eu só fico lendo, sem modificar nada. Dessa maneira, eu não preciso fazer um deploy inteiro de um novo banco para cada branch — eu só crio uma cópia dos metadados, não copio todos os gigabytes de dados do zero. E enquanto eu tô só lendo, eu fico lendo aquela cópia dos metadados; quando eu preciso fazer alteração, eu só crio um bloco novo específico daquela área que eu quero alterar, no momento exato em que essa alteração precisa ser feita. Aí eu vou ter, como dados duplicados, somente aquela parte que foi modificada.

E aí o grande pulo do gato está no seguinte: sempre que eu for fazer um novo teste — fazer o deploy da minha branch no ambiente de testes — esse deploy vai triggar a execução de uma cópia do meu banco de dados de staging. Eu vou ter um banco de dados de staging só, para não correr o risco de copiar direto do de produção (até porque em produção pode ter dados reais dos clientes). Então o meu banco de dados de staging seria o meu banco principal, que eu fico observando.

A cada branch nova que eu fosse criar — tipo a branch em que eu tô mexendo na feature de login, de billing, fazendo migration nos users — um deploy novo vai ser feito nesse ambiente, com uma cópia do banco específica para cada uma dessas branches. Só que essa cópia do banco vai estar funcionando nessa técnica de copy-on-write, onde ela não é de fato uma cópia completa do banco original com todos os dados. Então, se tivesse 10 GB, não seriam três cópias de 10 GB — na verdade é só uma cópia do esquema, com ponteiros para os dados originais, para fazer a leitura.

Quando um dado for alterado nessa branch — se na branch de login eu fui lá e modifiquei o login de algum usuário — eu vou criar uma cópia específica só daquele bloco, da representação daquele usuário, e vou fazer um *write* em cima. Esse write vai ser lido somente pela minha branch. A mesma coisa caso eu faça mudança nos esquemas dos bancos: essa mudança de esquema vai existir somente pra minha branch específica.

No final, eu consigo fazer testes muito mais seguros, e ter certeza de que a integração das modificações da minha branch está pronta para ir pra produção. Aí eu faço o merge e o deploy somente da minha branch, com muito mais segurança e confiança de que aquelas alterações estão seguras para ir pra produção — porque eu sei que todo o ambiente que eu tava testando era uma emulação 100% fiel ao ambiente de produção, só com as minhas alterações adicionadas, com esse esquema aprovado. Com tudo certo, eu jogo isso pra produção, fazendo alteração das tabelas, das queries e dos testes que eu precisar fazer. Opcionalmente, eu também poderia copiar os dados que eu modifiquei, caso eu queira levar isso pra produção.

## Exemplo prático: o portal fernandakipper.com com Neon

Só que falar é muito fácil, né? Então eu quero mostrar um exemplo bem legal de algo que a gente fez aqui na nossa empresa, inclusive no nosso portal de cursos aqui do canal — o `fernandakipper.com`, um portal de cursos gratuitos. Aqui não tem muito estresse, não tem muito mistério nessas tabelas, são relativamente simples, e a gente não tem muitos devs nem muitos deploys. Mas mesmo assim a gente já aplicou essa técnica de database branching, porque, quando a gente estava implementando as novas trilhas de aprendizagem e mexendo nos cursos com certificado, eu e o Léo estávamos fazendo muitas modificações no esquema do banco — cada um trabalhando em uma parte da aplicação — e a gente estava tendo muito esses conflitos no banco de dados de teste compartilhado que a gente tinha.

Ao utilizar a técnica de branching, a gente conseguiu evoluir cada um na sua feature de boa, realizando quantas migrations precisasse no banco de testes, até que tivesse OK para ir para produção. E a gente fez isso utilizando o banco de dados **Neon**.

Para quem não conhece, Neon Database é um backend para aplicações backend — na verdade um Postgres backend em nuvem, escalável à medida que você for utilizando. À medida que o número de requisições vai aumentando, você consegue ir aumentando a quantidade de recursos, e também diminuindo, caso esteja com menos requisições — então você só vai gastando à medida que usa. Na verdade ele funciona como uma plataforma backend completa, onde a gente consegue integrar não só a parte do banco de dados, mas também outras funcionalidades como gerenciamento de autenticação, AI gateway, storage de objetos/arquivos etc. E a gente tá usando aqui especificamente para hospedar o nosso banco Postgres.

O que a gente fez: no nosso projeto, a gente tem dois projetos na home — **certificates dev** e **certificates app**. O `certificates app` é o nosso banco de dados de produção — a gente não mexe ali, a gente não tá criando as branches lá. A gente tá criando as branches no `certificates dev`. Esse `certificates dev` tem uma branch que é a `main` — é o esquema que tá em produção. Ou seja, eu tenho dois ambientes: um ambiente de produção, que só tem as coisas de prod, e no meu ambiente de testes/preview eu também tenho uma cópia do esquema de produção, justamente pra ter esse banco de staging, digamos assim — o meu banco estável de staging que vai ser utilizado para criar cada uma das cópias a cada deploy.

A cada branch nova que a gente cria lá no GitHub, a gente inicia o deploy na Vercel. Nos deployments do ambiente de preview, a cada branch nova que eu crio, ele cria uma cópia a partir dessa branch `main` do banco de dados, para eu utilizar naquele ambiente de preview. Então cada ambiente de preview lá na Vercel — um ambiente de testes novo — tem uma cópia do banco que não é uma cópia completa: ele só copia os metadados e tem um ponteiro para ler dos dados originais, e somente quando há alterações é que ele copia o bloco e faz o rewrite em cima. Essa integração toda com a Vercel acontece de forma automática também.

Na Vercel, em Storage, eu tenho a minha conexão com o Neon Database — a gente só configurou qual era a branch lá do GitHub que seria a minha branch com o esquema mãe. Para cada branch nova que eu vou fazendo deploy no ambiente de testes, ele cria uma cópia do esquema mãe, que é igual ao de produção, só que sem os dados de produção — a diferença é que não tem o dado dos usuários que utilizam a plataforma, são dados de mock que a gente colocou nessa branch, um *seed* que a gente fez. Claro, os dados dos nossos usuários são mais seguros, tem inclusive o outro banco (o de produção) com políticas de criptografia que a gente não aplica nesse aqui, porque esse é só um banco de teste com dados de teste também.

O bacana é que, a cada branch nova que eu vou criando, ela já vem com essa cópia dos dados de mock (o seed). Assim que o deploy finaliza — quando eu tenho um deploy *ready* — já tem, nesse ambiente, o link direto para o banco de testes que eu criei somente para essa branch. Essa alteração das variáveis de ambiente também é feita de forma automática, nesse caso, porque a Vercel tem integração automática com o Neon.

Se não tivesse essa integração automática, vocês teriam que desenvolver o próprio mecanismo para atualizar a variável de ambiente no momento do deploy: quando eu tivesse fazendo o deploy da branch específica, eu ia ter que primeiro criar essa cópia de copy-on-write, e com essa cópia teria que ter um novo endpoint de host (a password poderia continuar a mesma, mas o host muda), gerar uma nova connection string e usar essa string para atualizar a minha variável de ambiente, para que, quando a aplicação rodasse, ela estivesse olhando pro banco correto — o banco criado só para aquela branch. Como a Vercel faz isso automaticamente, a gente nem precisa se preocupar: ela já atualiza a `DATABASE_URL` para mim. E, com a `DATABASE_URL` atualizada, caso tenha alguma migration para rodar, essa migration já roda no momento do deploy também, tudo de forma automática.

Com isso, eu consigo ter um ambiente de testes que é exatamente uma cópia do meu ambiente de produção — com os mesmos cursos cadastrados que eu tenho em prod. Claro, os meus usuários, as informações de certificados emitidos, esse tipo de coisa de vendas, não vai ter nesse ambiente de teste — inclusive tem até menos cursos no de teste do que em prod (em prod a gente já tem uns 11 cursos; quando a gente criou o seed desse banco de testes só tinha 6, e a gente deixou assim mesmo). O importante é que aqui eu posso rodar quantas migrations eu quiser, quebrar esse banco de cima a baixo, e não vai ter risco nenhum, nem com o que o Léo tiver testando, nem com as coisas que vão pra produção.

## Como testar / conectar

Essa é a melhor técnica pra trabalhar com bancos de dados de teste, principalmente em aplicações que têm muitas modificações no esquema, com essa interação muito direta com o banco de dados.

Se você quiser criar uma conta gratuita no Neon Database para criar os seus bancos de dados, pros seus projetos pessoais ou até pra sua empresa, e começar a testar a solução deles: eles têm alguns créditos no free tier pra fazer os testes. Você pode criar bancos de dados Postgres, como eu mostrei aqui, ou utilizar qualquer uma das outras soluções que eles oferecem. Para conectar é super fácil: no botão "Connect" ele já gera a connection string para vocês conectarem o banco de dados. Caso forem fazer a integração com a Vercel, é só entrar na Vercel e integrar — fazer o connect — ou com qualquer outro serviço de hospedagem que estiverem utilizando, seja AWS, Hostinger, GCP etc. Aí é só pegar a connection string e colocar nas variáveis de ambiente, conectando a aplicação direto com o banco.

Vocês podem também rodar queries nos seus bancos de dados, direto no SQL Editor, para ver o que tá acontecendo, inspecionar as tabelas, fazer backup do banco, salvar snapshots — tudo pela plataforma deles. Na versão gratuita já dá pra explorar quase tudo que eles oferecem; algumas features ficam só pra quem tem assinatura Premium, mas criar o projeto e começar a testar já pode ser feito de forma gratuita.
