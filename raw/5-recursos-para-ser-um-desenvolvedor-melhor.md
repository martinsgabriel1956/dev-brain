# 5 (ou 6) Recursos Para Se Tornar um Desenvolvedor Melhor

## Contexto

Vídeo do Augusto Galego respondendo a um pedido recorrente da audiência: ferramentas e recursos para melhorar como desenvolvedor. Ele abre desafiando a sugestão-padrão (LeetCode), argumentando que o retorno sobre o esforço não é tão bom quanto o de outras fontes. No título ele diz "cinco" porque "cinco é o número mais bonito", mas lista seis recomendações.

---

## Recurso 1 — Documentação do Framework

A recomendação mais óbvia: ler a documentação do próprio framework/runtime que você usa no dia a dia (ex.: Node.js, Express, Django, .NET).

Exemplo dado: para construir boas aplicações com Node + Express, é necessário entender como o event loop do Node funciona — isso só vem lendo a documentação oficial, não de atalhos.

---

## Recurso 2 — roadmap.sh

Repositório/produto no GitHub com 284 mil estrelas e mais de 1.000 contribuidores — um dos projetos mais estrelados do GitHub. Resolve o problema de "não sei por onde estudar".

Funciona como um mapa de conhecimento por área (ex.: front-end): lista o que aprender, na ordem — HTML, CSS, como a internet funciona, HTTP, layouts responsivos, npm/pnpm, JavaScript, frameworks (React, Vue, Angular). Cada tópico do roadmap linka artigos e vídeos de referência.

**Ressalva do speaker:** não é o recurso mais profundo em cada tópico individual, mas é excelente como direcionamento — funciona como uma aproximação do que uma faculdade ensinaria (protocolos, fundamentos), o que o torna ainda mais valioso para quem não fez faculdade.

Está todo em inglês, o que reforça a recomendação lateral do vídeo: **estudar inglês** ajuda muito na área, mesmo para quem não pretende trabalhar fora do país.

---

## Recurso 3 — CS50 (Harvard)

Curso gratuito de Harvard, recomendado especialmente para quem não fez faculdade. Dá uma base equivalente à formação acadêmica em fundamentos de ciência da computação. Também em inglês.

---

## Recurso 4 — Livros

O speaker avalia livros pela Amazon considerando preço/benefício, não só qualidade:

- **Entendendo Algoritmos** — recomendado para todo mundo, principalmente quem estuda para entrevistas estilo LeetCode. Já revisado no canal antes.
- **Cracking the Coding Interview** — caro (~R$269 na época), é "o livro do Ratinho" mais completo, inclui system design. É o livro padrão para quem estuda para Fang, mas é maçante; o speaker começou e não terminou por não estar nesse momento de carreira agora.
- **Introduction to Algorithms** — para quem quer se aprofundar muito em algoritmos. O speaker só folheou, achou denso demais e não recomenda com confiança por não tê-lo lido de fato.
- **The Pragmatic Programmer** — caro na versão em inglês (~R$428) mas considerado excelente, um dos melhores livros de "filosofia de software".
- **Clean Code** — mencionado com reserva explícita: o autor é polêmico/cancelado, as dicas são "metade boas, metade duvidosas". Se fosse montar uma lista dos 10 melhores livros, este não entraria.
- **Refactoring (Martin Fowler)** — recomendação forte e sem ressalvas, considerado excelente e com bom custo-benefício (~R$10 na Amazon no momento da gravação).
- **Arquitetura de Software: As Partes Difíceis** — recomendado com frequência no canal; destaque para o custo-benefício (conteúdo difícil de achar em outro lugar, apesar de leitura densa).

---

## Recurso 5 — Cursos (Udemy)

Para quem aprende melhor via curso estruturado: Udemy tem cursos bons na faixa de R$20–30 (aproveitando promoções). Instrutor citado como referência de qualidade: Maximilian Schwarzmüller.

**Regra de preço:** nunca pagar cursos de R$5.000–10.000 para aprender uma tecnologia específica (ex.: Node) — esse investimento alto só faz sentido para algo como faculdade, não para um curso avulso.

O speaker diz preferir aprender de forma multimodal — curso + documentação + projeto prático simultaneamente — por absorver melhor assim.

---

## Recurso 6 — Contribuir com Open Source

Contribuir com projetos open source que você já usa no dia a dia. Exemplo pessoal: o speaker usa o Excalidraw (aparece nos próprios vídeos) e conhece um bug específico (Ctrl+Z ao colar uma imagem) que poderia reportar/corrigir, mas ainda não abriu a issue apesar do projeto já ter 1.400 issues abertas.

**Duas formas de aplicar a ideia:**
1. Inspirar-se num projeto open source para criar o seu próprio (o speaker cita ter criado um "roadmap de investimentos" inspirado na ideia do roadmap.sh).
2. Contribuir diretamente com projetos de terceiros — procurar por issues marcadas `good first issue` ou `good first fix` no GitHub como ponto de entrada.

**Conclusão do vídeo:** nenhum desses recursos substitui escrever muito software na prática — ler documentação e fazer cursos não substitui a prática de escrever código continuamente.
