# Capítulo 1 — Introdução (É Tudo Sobre Complexidade)

Escrever software de computador é uma das atividades criativas mais puras da história da raça humana. Os programadores não estão limitados por restrições práticas, como as leis da física; podemos criar mundos virtuais empolgantes com comportamentos que nunca poderiam existir no mundo real. A programação não exige grande habilidade física ou coordenação, como o balé ou o basquete. Tudo o que a programação exige é uma mente criativa e a capacidade de organizar seus pensamentos. Se você consegue visualizar um sistema, provavelmente consegue implementá-lo em um programa de computador.

Isso significa que a maior limitação ao escrever software é a nossa capacidade de entender os sistemas que estamos criando. À medida que um programa evolui e adquire mais recursos, ele se torna complicado, com dependências sutis entre seus componentes. Com o tempo, a complexidade se acumula e fica cada vez mais difícil para os programadores manterem todos os fatores relevantes em mente enquanto modificam o sistema. Isso desacelera o desenvolvimento e leva a bugs, que atrasam ainda mais o desenvolvimento e aumentam seu custo. A complexidade aumenta inevitavelmente ao longo da vida de qualquer programa. Quanto maior o programa e quanto mais pessoas trabalharem nele, mais difícil será gerenciar a complexidade.

Boas ferramentas de desenvolvimento podem nos ajudar a lidar com a complexidade, e muitas ferramentas excelentes foram criadas nas últimas décadas. Mas há um limite para o que podemos fazer apenas com ferramentas. Se quisermos tornar mais fácil escrever software, para que possamos construir sistemas mais poderosos de forma mais barata, precisamos encontrar maneiras de tornar os softwares mais simples. A complexidade ainda aumentará com o tempo, apesar de nossos melhores esforços, mas designs mais simples nos permitem construir sistemas maiores e mais poderosos antes que a complexidade se torne avassaladora.

Existem duas abordagens gerais para combater a complexidade, ambas serão discutidas neste livro. A primeira abordagem é eliminar a complexidade tornando o código mais simples e óbvio. Por exemplo, a complexidade pode ser reduzida eliminando casos especiais ou usando identificadores de maneira consistente.

A segunda abordagem para a complexidade é encapsulá-la, de forma que os programadores possam trabalhar em um sistema sem serem expostos a toda a sua complexidade de uma só vez. Essa abordagem é chamada de _design modular_. No design modular, um sistema de software é dividido em _módulos_, como classes em uma linguagem orientada a objetos. Os módulos são projetados para serem relativamente independentes uns dos outros, para que um programador possa trabalhar em um módulo sem ter que entender os detalhes de outros módulos.

Como o software é muito maleável, o design de software é um processo contínuo que abrange todo o ciclo de vida de um sistema de software; isso torna o design de software diferente do design de sistemas físicos, como edifícios, navios ou pontes. No entanto, o design de software nem sempre foi visto dessa forma. Nos primórdios da programação, o design frequentemente se concentrava no início de um projeto, assim como ocorre em outras disciplinas da engenharia. O extremo dessa abordagem é chamado de _modelo cascata_ (waterfall model), no qual um projeto é dividido em fases discretas, como definição de requisitos, design, codificação, testes e manutenção. No modelo cascata, cada fase é concluída antes que a próxima fase comece; em muitos casos, pessoas diferentes são responsáveis por cada fase. Todo o sistema é projetado de uma só vez, durante a fase de design. O design é congelado no final dessa fase, e o papel das fases subsequentes é estruturar e implementar esse design.

Infelizmente, o modelo cascata raramente funciona bem para software. Os sistemas de software são intrinsecamente mais complexos que os sistemas físicos; não é possível visualizar o design de um grande sistema de software bem o suficiente para entender todas as suas implicações antes de construir qualquer coisa. Como resultado, o design inicial terá muitos problemas. Os problemas não se tornam aparentes até que a implementação esteja bem avançada. No entanto, o modelo cascata não é estruturado para acomodar grandes mudanças de design nesse ponto (por exemplo, os designers podem ter passado para outros projetos). Assim, os desenvolvedores tentam contornar os problemas sem alterar o design geral. Isso resulta em uma explosão de complexidade.

Por causa desses problemas, a maioria dos projetos de desenvolvimento de software hoje usa uma abordagem incremental, como o _desenvolvimento ágil_, na qual o design inicial se concentra em um pequeno subconjunto da funcionalidade geral. Esse subconjunto é projetado, implementado e, em seguida, avaliado. Problemas com o design original são descobertos e corrigidos, e então mais alguns recursos são projetados, implementados e avaliados. Cada iteração expõe problemas com o design existente, que são corrigidos antes que o próximo conjunto de recursos seja projetado. Ao distribuir o design dessa forma, os problemas com o design inicial podem ser corrigidos enquanto o sistema ainda é pequeno; os recursos posteriores se beneficiam da experiência adquirida durante a implementação dos recursos anteriores, para que tenham menos problemas.

A abordagem incremental funciona para software porque o software é maleável o suficiente para permitir mudanças significativas de design no meio da implementação. Em contraste, grandes mudanças de design são muito mais desafiadoras para sistemas físicos: por exemplo, não seria prático mudar o número de torres de sustentação de uma ponte no meio da construção.

O desenvolvimento incremental significa que o design de software nunca está terminado. O design acontece continuamente ao longo da vida de um sistema: os desenvolvedores devem estar sempre pensando em questões de design. O desenvolvimento incremental também significa um redesign contínuo. O design inicial para um sistema ou componente quase nunca é o melhor; a experiência inevitavelmente mostra maneiras melhores de fazer as coisas. Como desenvolvedor de software, você deve estar sempre atento a oportunidades para melhorar o design do sistema em que está trabalhando e deve planejar gastar uma fração do seu tempo em melhorias de design.

Se os desenvolvedores de software devem sempre pensar em questões de design, e reduzir a complexidade é o elemento mais importante do design de software, então os desenvolvedores de software devem sempre pensar sobre complexidade. Este livro é sobre como usar a complexidade para guiar o design de software ao longo de sua vida útil.

Este livro tem dois objetivos principais. O primeiro é descrever a natureza da complexidade do software: o que significa “complexidade”, por que ela importa e como você pode reconhecer quando um programa tem complexidade desnecessária? O segundo, e mais desafiador, objetivo do livro é apresentar técnicas que você pode usar durante o processo de desenvolvimento de software para minimizar a complexidade. Infelizmente, não existe uma receita simples que garanta excelentes designs de software. Em vez disso, apresentarei uma coleção de conceitos de alto nível que beiram o filosófico, como “as classes devem ser profundas” ou “elimine os erros desde a concepção”. Esses conceitos podem não identificar imediatamente o melhor design, mas você pode usá-los para comparar alternativas de design e orientar sua exploração do espaço de design.
## 1.1 Como usar este livro

Muitos dos princípios de design descritos aqui são um tanto abstratos, o que pode dificultar sua compreensão sem olhar para um código real. Tem sido um desafio encontrar exemplos que sejam pequenos o suficiente para incluir no livro, mas grandes o bastante para ilustrar problemas em sistemas reais (se você encontrar bons exemplos, por favor, envie-os para mim). Sendo assim, este livro por si só pode não ser suficiente para você aprender a aplicar os princípios.

A melhor forma de usar este livro é em conjunto com revisões de código. Quando você ler o código de outras pessoas, pense se ele está em conformidade com os conceitos discutidos aqui e como isso se relaciona com a complexidade do código. É mais fácil enxergar problemas de design no código de outra pessoa do que no seu próprio. Você pode usar os _sinais de alerta_ descritos aqui para identificar problemas e sugerir melhorias. Revisar código também apresentará a você novas abordagens de design e técnicas de programação.

Uma das melhores formas de aprimorar suas habilidades de design é aprender a reconhecer _sinais de alerta_: indícios de que um trecho de código provavelmente está mais complicado do que precisaria ser. Ao longo deste livro, vou apontar _sinais de alerta_ que sugerem problemas relacionados a cada grande questão de design; os mais importantes estão resumidos no final do livro. Você poderá usá-los quando estiver programando: ao notar um _sinal de alerta_, pare e procure por um design alternativo que elimine o problema. Ao tentar essa abordagem pela primeira vez, talvez você precise testar diversas alternativas de design antes de encontrar uma que resolva a questão. Não desista facilmente: quanto mais alternativas você testar antes de consertar o problema, mais você aprenderá. Com o tempo, você vai perceber que o seu código terá cada vez menos _sinais de alerta_, e seus designs ficarão cada vez mais limpos. Sua experiência também mostrará outros sinais que você poderá usar para identificar problemas de design (eu adoraria ouvir sobre eles).

Ao aplicar as ideias deste livro, é importante ter moderação e bom senso. Toda regra tem suas exceções, e todo princípio tem seus limites. Se você levar qualquer ideia de design ao extremo, provavelmente acabará em uma situação ruim. Designs bonitos refletem um equilíbrio entre ideias e abordagens concorrentes. Vários capítulos possuem seções intituladas "Indo longe demais" (_Taking it too far_), que descrevem como reconhecer quando você está exagerando na dose.

Quase todos os exemplos neste livro estão em Java ou C++, e grande parte da discussão foca no design de classes em uma linguagem orientada a objetos. No entanto, as ideias se aplicam a outros domínios também. Quase todas as concepções relacionadas a métodos podem igualmente ser aplicadas a funções em uma linguagem sem recursos de orientação a objetos, como C. As ideias de design também valem para módulos que não sejam classes, como subsistemas ou serviços de rede.

Com esse contexto, vamos discutir com mais detalhes o que causa a complexidade e como tornar os sistemas de software mais simples.

### Notas do Tradutor (N.T.)

- **Revisões de código:** Tradução de _code reviews_, uma prática fundamental na engenharia de software onde desenvolvedores analisam o código uns dos outros para garantir qualidade.
    
- **Sinais de alerta:** Tradução escolhida para _red flags_, referindo-se a antipadrões ou "cheiros no código" (_code smells_) que indicam falhas estruturais ou complexidade desnecessária.
