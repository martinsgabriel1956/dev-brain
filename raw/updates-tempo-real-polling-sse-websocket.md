## Polling

A nossa primeira estratégia é o polling, super simples, super básico — a maioria das pessoas já viu ou já implementou e sabe como funciona. O polling nada mais é do que, a cada X segundos, disparar uma requisição HTTP para o servidor perguntando se tem alguma atualização, alguma coisa nova. Por exemplo, a gente pode perguntar se tem notificações novas para mostrar pro usuário: coloca um intervalo no código e, a cada 5 segundos, faz uma chamada para verificar se tem notificação nova. Se existir, a gente atualiza a tela e mostra "1, 2, 3 notificações novas" na UI.

Para fluxos não críticos, sistemas de notificações, sistemas de relatórios, quando a gente não tem tantos usuários logados ao mesmo tempo, o polling é uma estratégia super válida, porque é super simples, não é nada complexo, e já supre a necessidade momentânea — a gente não precisa saber exatamente o momento exato em que uma notificação chegou ou que um relatório ficou pronto. Tudo bem ter um delay de 3, 5, 8 segundos, o polling já supre esse tipo de necessidade.

Lembro que, lá no começo da minha carreira, quando era júnior, eu tive que implementar um sistema de polling para uma tela de relatório, para o usuário não precisar recarregar a tela para ver o relatório disponível para baixar. Eu olhava e falava "nossa, que arquitetura horrível, vai ficar desperdiçando requisições e não vai acontecer nada com a tela na maior parte do tempo". Até eu ver um desenvolvedor sênior, com mais de 8-10 anos de experiência, falando que o polling é exatamente feito para esse tipo de situação. E senioridade é sobre isso: entender que problemas simples requerem soluções simples. Se a gente precisar de algo mais avançado, existe uma solução mais apropriada, mas, para sistemas desse nível, o polling é totalmente razoável — se a demanda é muito baixa, não tem porque colocar um WebSocket para atualizar em tempo real que o relatório ficou pronto, quando tem 10 usuários usando o sistema.

Não tenha medo de citar isso na entrevista: se o entrevistador falar que tem 1000 usuários conectados, mas é só um sistema simples para mostrar uma notificação, o polling é perfeito para isso — não tem porque inventar falar de Server-Sent Events, é isso que ele espera de você.

Só que, claro, a maior parte das coisas possui um trade-off, e qual é o trade-off do polling? Alta latência e pouca precisão. Imagina se a gente fosse fazer polling num sistema do Uber, atualizando a localização do motorista a cada 10 segundos — o carro ia ficar pulando, saltando, em vez de a gente ver exatamente a rua que ele tá virando, num movimento suave, em tempo real. Então o polling não é adequado para tipos de sistemas que exigem essa coordenação perfeita em tempo real, e também porque acaba desperdiçando recursos quando tem muitos usuários ativos — o polling também não vai escalar. Funciona para notificações, mas se tiverem 2 milhões de usuários conectados ao mesmo tempo, o polling vai acabar exigindo muito do servidor com requisições fantasma que não estão fazendo nada, mas estão acessando o banco e consumindo recurso do banco e do servidor. Para esse tipo de situação, ele também não é muito recomendado — seria para uma aplicação de médio ou baixo porte, para coisas mais simples que não são tão sensíveis à latência.

### Long polling

Vale também citar uma outra estratégia, semelhante ao polling, que é o long polling. O long polling é a mesma coisa que o polling — fazendo uma chamada HTTP pro servidor — só que o servidor, em vez de responder instantaneamente com o resultado positivo ou negativo, segura essa conexão por 20-30 segundos e, quando tiver alguma coisa para devolver pro cliente, devolve, e aí o cliente atualiza quase que em tempo real. É um pouco mais preciso que o polling porque mantém a conexão aberta e recebe exatamente na hora que o servidor tem alguma coisa nova, só que também é algo que não escala, não foi feito para escalar infinitamente — tanto que a maioria das empresas, quando querem esse tipo de estratégia, recorrem para o próximo conceito.

## Server-Sent Events (SSE)

Quando a gente quer uma atualização mais precisa, quando mudou alguma coisa no servidor e automaticamente e instantaneamente já muda no cliente, a gente usa a estratégia de SSE, o Server-Sent Events. Ele é perfeito para quando a gente quer ficar esperando alguma coisa acontecer no servidor, alguma alteração, e atualizar o cliente de maneira instantânea, sem mais delay, sem mais espera.

Como que a gente faz isso na API do browser? Tem uma classe especial, o `EventSource`, que faz uma solicitação HTTP para algum endpoint do servidor e fica escutando alterações nesse endpoint. Sempre que ele envia que alguma coisa mudou — nesse caso, uma notificação nova chegou — a gente parseia esses dados e mostra a notificação pro usuário, tudo de forma instantânea.

Server-Sent Events serve, por exemplo, para aplicações de mercado financeiro, onde a gente quer ficar acompanhando o preço das ações em tempo real — não pode ter delay, tem que saber exatamente quando tá subindo ou descendo o preço; ou gráficos onde a gente quer acompanhar o estado da aplicação, do servidor, o uso de recursos do banco de dados em tempo real. SSE é perfeito para isso, porque é simples e escala muito mais facilmente do que o polling.

O trade-off do Server-Sent Events é que ele só trafega texto, não trafega binário (diferente do próximo conceito, que tem uma capacidade a mais na trafegação dos dados), e, principalmente, é uma comunicação unidirecional — sempre do servidor pro cliente, nunca ao contrário. O cliente nunca consegue conversar com o servidor e enviar coisas para lá, é sempre o cliente escutando os dados que o servidor envia. Para certos tipos de aplicações, como chats, onde a gente tem um usuário enviando e o outro recebendo em tempo real, e depois o outro responde, já não faz sentido, não dá pra usar, porque é sempre o servidor que manda pro cliente e não o contrário. Para isso a gente vai precisar de uma outra estratégia.

## WebSocket

O nosso grande e querido WebSocket permite conexões bidirecionais: tanto o cliente quanto o servidor conseguem trocar dados entre si — eu, como cliente, consigo mandar dados pro servidor, e o servidor consegue mandar dados para mim.

Como funciona? Assim como o Server-Sent Events, existe uma Web API própria para trabalhar com WebSocket. O protocolo é diferente, não é mais HTTP: a gente cria um `new WebSocket` apontando pro host, e consegue tanto escutar por eventos que o servidor manda (sempre que ele enviar, a gente converte a mensagem e mostra no chat) quanto mandar dados pro servidor (`chat.send`, mandando uma mensagem de resposta). A gente consegue ter essa troca e alcançar uma outra gama de aplicações, como chats e colaborações em tempo real. Se você se perguntava o que o Google Docs e o Figma usam por baixo dos panos para ter esse tipo de aplicação, é exatamente WebSocket.

Como vantagem, a gente tem a conexão bidirecional, já totalmente distinta das outras estratégias; a latência, assim como no Server-Sent Events, é praticamente instantânea, abaixo de 500ms; e, além do texto, ele trafega frames binários, se for necessidade da aplicação.

### Como funciona a comunicação do WebSocket

O protocolo é diferente porque o WebSocket começa com uma solicitação HTTP, só que no cabeçalho da requisição ele manda um `Upgrade: websocket` e um `Connection: Upgrade`. O que ele faz é abrir essa conexão inicial HTTP, mas depois atualiza para uma conexão TCP, e mantém essa conexão aberta com o servidor num formato de túnel, de tunelamento — e aí os dois conseguem livremente trocar dados entre si. Existe também um cabeçalho de verificação (uma key) que é enviado para checar se o servidor é capaz de lidar com conexões WebSocket: ele manda a key pro servidor validar, e depois revalida essa key pra saber se o servidor converteu ela certo. Com isso, a gente consegue manter a conexão aberta com esse protocolo específico, que torna tudo muito eficiente e rápido.

Mas, como nem tudo são flores, também temos dificuldades e trade-offs ao trabalhar com WebSocket, e o principal deles é que é mais complexo e precisa de infraestrutura específica.

### Escalando WebSocket: Load Balancer de camada 4

Vamos imaginar o seguinte cenário: um servidor com 16 cores, 32GB de RAM, mensagens com tamanho de mais ou menos 1KB (mais ou menos 1000 caracteres), e todas as pessoas conectadas gerando mais ou menos 100.000-1000 mensagens por segundo. Com base nesses dados, a gente chega a mais ou menos 300-500 mil conexões simultâneas nesse servidor, o que é um valor muito legal. Só que quantas conexões simultâneas o WhatsApp mantém aberta por dia? Muito mais do que isso. Para isso a gente vai precisar expandir os servidores e fazer a replicação, pra suprir toda a demanda de usuários.

Assim como qualquer outra aplicação, a gente vai replicar esses servidores pra ter mais redundância e permitir que mais usuários se conectem. Pra fazer o roteamento dos usuários, a gente vai precisar de um load balancer — só que esse load balancer tem uma característica: não vai ser um load balancer convencional. Normalmente, quando temos servidores servindo requisições HTTP normais, chamadas de API normais, eles são load balancers de camada 7 (layer 7), atuando na camada de aplicação. Para WebSocket é diferente: a gente vai ter que usar load balancers de camada 4 (layer 4). Isso faz toda a diferença numa entrevista.

Load balancers possuem normalmente sete camadas: as chamadas HTTP acontecem na camada 7, e as chamadas WebSocket acontecem na camada 4. Por que o WebSocket não pode acontecer na camada 7? Porque, quando um cliente faz uma requisição pro servidor e o load balancer tá no meio, ele pega essa requisição, abre, lê os cabeçalhos, empacota de novo, e faz uma outra chamada pro servidor, meio que redirecionando. Isso não funciona para WebSocket porque acaba quebrando o fluxo, que precisa ser constante e contínuo. O layer 4 permite que o load balancer não abra nem faça nada com o conteúdo — ele só redireciona pro servidor que tiver com menos conexões, por exemplo (uma estratégia de balanceamento de carga verificando qual servidor tem menos conexões abertas no momento). É por isso que se usa layer 4 e não layer 7.

Com o load balancer de layer 4 redirecionando pros servidores, em vez de aguentar só 500 mil conexões, a gente aguenta 1, 2, 2.5 milhões de conexões simultâneas. Isso já é muita coisa. Só que tem algo que acontece aqui que é exatamente onde o entrevistador vai querer saber se você tem o conhecimento além de só falar que WebSocket resolve o problema de tempo real.

### Comunicação entre servidores: Redis Pub/Sub

O usuário 1 tá conversando com o usuário 2, só que, na hora de rotear, o load balancer decidiu jogar o usuário 1 pro servidor 1 e o usuário 2 pro servidor 4. Como eles vão conversar entre si? Como o servidor 4 vai saber que precisa mandar uma mensagem pro servidor 1 para devolver? Se os dois estivessem conectados no mesmo servidor, ótimo, resolvido — mas quando temos vários servidores, como eles se comunicam entre si?

Para resolver esse problema, muitas empresas utilizam uma estratégia que é meio que um padrão (não é a única solução — dá pra usar Raft, dá pra usar Kafka), mas muitas escolhem por causa da simplicidade: pub/sub com Redis. O Redis ataca exatamente esse problema da comunicação entre os servidores.

Basicamente: quando o usuário 1 se conecta no servidor, ele se inscreve em um tópico do Redis, chamado por exemplo `user:1` (o ID do usuário). Esse tópico é como se fosse um listener — quando a pessoa fica escutando naquele tópico, sempre que alguém publica alguma coisa nesse tópico, o tópico recebe essa publicação, esse evento, essa mensagem. Da mesma forma, o usuário 2 se inscreve em um tópico com o ID dele no servidor 4.

Quando o usuário 1 lista todas as conversas que tinha no frontend e clica na conversa com o usuário 2, ele já tem acesso ao ID do usuário 2 (porque já listou previamente), e carrega esse ID na conversa porque vai precisar dele no backend. Quando aperta enter e manda a mensagem pro servidor, o servidor publica essa mensagem no tópico `user:2`. Por o usuário 2 estar inscrito nesse tópico, ele recebe a mensagem do usuário 1. Da mesma forma, quando ele publica no tópico do usuário 1, por o usuário 1 estar inscrito, ele recebe. É assim que a gente mantém a conexão entre os dois usuários, independente do servidor em que eles caírem — o Redis funciona como a nossa central, o broker de mensagens/eventos, com base em inscrições em tópicos.

Isso não funciona só para usuário, funciona para grupos também: por exemplo, um grupo com 10 pessoas, todas inscritas no tópico `group:123`. Sempre que alguém manda uma mensagem nesse tópico, todos os inscritos recebem, os servidores todos atualizam ao mesmo tempo e mandam pro front. Isso funciona para qualquer coisa que seja um tópico no Redis: alguém publica, todos os inscritos recebem.

Na maioria das entrevistas, as pessoas param aqui — sabem usar WebSocket, sabem que existe Server-Sent Events, sabem os conceitos, mas não sabem o "depois". Saber que o load balancer precisa ser layer 4 para conexões WebSocket, e entender como os servidores se comunicam entre si (a segunda etapa da comunicação), é fenomenal.

### E se o usuário estiver offline?

Tem uma pergunta que sempre cai nas entrevistas quando o assunto é atualizações em tempo real de chats: e se o usuário estiver offline, como ele vai receber as mensagens? Porque, se alguém publica uma mensagem no Redis e essa pessoa não está inscrita, essa mensagem se perde, não tem como recuperar. Como resolver o caso de pessoas com o celular desligado?

A resposta é simples (existem outras maneiras, mas essa é uma estratégia bem razoável que funciona perfeitamente): a gente tem uma tabela no banco de mensagens pendentes. Sempre que for publicar uma mensagem no Redis, a gente também salva essa mensagem nessa tabela. Se o usuário não estiver online, ele não recebe em tempo real pela inscrição no Redis, mas tem esse backup na tabela. Assim que ele volta a se conectar, a aplicação faz uma chamada pra essa tabela, verifica se tem algum dado pendente e, se tiver, devolve tudo num pacote — e ele consegue ver todas as mensagens que estavam pendentes.

Existem dois vieses nesse tipo de estratégia: tem quem mantenha essas mensagens armazenadas como histórico no banco de dados, e tem quem prefira deixar isso de forma temporária. Por exemplo, o WhatsApp (se não me engano) não mantém essas mensagens salvas no banco dele, por questões legais — não quer salvar dados sensíveis por conta de algum vazamento. Ele deixa a mensagem de forma temporária e, assim que você pega todas as mensagens depois que estava offline, ele deleta tudo, garantindo que você já tem tudo no seu telefone (faz o backup mensal, etc.) e mantém o lado dele limpo, sem dados sensíveis armazenados.

Outra alternativa é colocar um timestamp nas mensagens: "eu só recebi até essa última mensagem, me dá tudo que veio depois dela enquanto eu estava offline" — a gente faz esse cálculo, pega todas as mensagens depois desse timestamp e devolve pro usuário.

## Resumo

Com isso a gente termina todos os conceitos e estratégias pra lidar com real-time updates: polling, Server-Sent Events, WebSockets, como funciona o load balancer L4 e por que ele precisa ser nessa camada especificamente (por causa da conexão TCP que o WebSocket tem, que precisa desse tunelamento constante), como os servidores se comunicam entre si, e como lidamos com usuários offline. Vale deixar claro que o Server-Sent Events também pode usar Redis Pub/Sub para essa mesma comunicação entre servidores, quando algo acontece em um servidor mas o usuário está conectado a outro servidor para receber o evento via SSE.

Os principais erros que as pessoas cometem durante as entrevistas são exatamente esses: não sabem lidar com a escala horizontal de servidores, não citam como funciona essa segunda parte (como os servidores vão se comunicar entre si, que mecanismo vão usar), não sabem lidar com o caso do usuário offline, ou simplesmente travam quando o entrevistador pergunta.

Vale lembrar também que polling não é uma estratégia ruim — é uma estratégia simples para um problema simples, e às vezes é exatamente isso que o entrevistador quer de você. Você não vai sair metendo um monte de infraestrutura de WebSocket para um sistema que tem 100 usuários ativos, não faz sentido. Muitas vezes o entrevistador quer saber se você identifica o problema que está sendo exigido de você, qual solução implementar para aquele caso, e aos poucos ele vai evoluindo o cenário ("e se tivéssemos 100.000 usuários ativos diariamente?"). É progressivo — não caia na cilada de usar uma arquitetura super forte para um sistema super simples.

E, super importante: sempre que estivermos trabalhando com WebSockets, usamos load balancers de layer 4, e não de layer 7 — extremamente importante, vai garantir pontos a mais na entrevista.
