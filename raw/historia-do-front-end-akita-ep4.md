## A estrutura mais simples: DNS, TCP, portas

Quando você abre o navegador e digita `https://meusite.com.br`, ele faz dezenas de operações, mas no mínimo precisa **traduzir o domínio em endereço IP**. Quem faz isso é o servidor de **DNS** (*Domain Name Server*), para onde a configuração de rede do seu computador aponta. DNS é como uma lista telefônica: traduz nomes em números. Depois, cabe à rede (roteadores, provedores) conectar seu navegador ao servidor. A internet funciona porque todas as pontas falam o mesmo formato de mensagens (um **protocolo**), e o que nos interessa é o **TCP/IP**.

Com o endereço, o navegador encontra o servidor certo no mundo. Em resumo: um **cliente TCP** (o navegador) liga a um **servidor TCP** que fica escutando uma **porta**. Todo servidor web que serve HTML é um programa que, ao subir, se liga a uma porta (número de 1 a ~65 mil). A convenção: servidor web escuta na **80**; SSH na **22**; HTTPS na **443**; servidores de desenvolvimento como Node.js, Rails e Java usam portas como **3000, 5000, 8080**. Não há nada de mágico: os números são arbitrários, escolhidos anos atrás; qualquer porta serve, contanto que haja algo escutando. Simplifiquei bastante; na faculdade o exercício é escrever um programa que escuta numa porta e outro que se conecta nela — é aí que nasce a semente de um servidor web e de um navegador.

## O servidor web mais simples (e o mais inseguro)

O servidor web mais simples **lê um arquivo da máquina e o serve**. O endereço completo é a **URL** (*Uniform Resource Locator*): protocolo + domínio + caminho de um arquivo. Antigamente você via endereços como `site-da-faculdade.edu/~josebarquinho`; o `~` é atalho para o diretório home do usuário (`/home/jose`), como você sabe se estudou Linux no episódio anterior. Esse é o servidor mais simples e, como sabemos hoje, o mais bugado em segurança: mapeia direto a URL para um caminho no sistema operacional sem nenhuma checagem, e dava para ficar tentando achar jeitos de vasculhar arquivos do usuário que ele julgava não públicos — e a gente fazia isso mesmo, para achar brechas.

Quando o navegador (um exemplo de cliente TCP) recebe esse `.html`, traduz as marcações em elementos visuais. Como existe o elemento de link, o `<a href>` (âncora + *hypertext reference*), nasce o conceito de **hipertexto**: um texto com links para outros textos. No começo ninguém queria visual, só disponibilizar textos linkando outros textos. Assim nasce a **World Wide Web (WWW)**.

## CGI: nascem os sites dinâmicos

Era inevitável o próximo passo: e se, em vez de digitar o nome de um arquivo `.html`, eu digitar o nome de um **executável** (um binário, `.exe` no Windows)? Num servidor antigo isso daria erro. Mas alguém fez um dos primeiros servidores que, quando pedem um executável, em vez de ler o arquivo e cuspir o conteúdo, **executa o programa no servidor e devolve o resultado**, que esperamos ser HTML. Para o navegador não faz diferença se pedimos um executável ou um arquivo texto, contanto que a resposta seja HTML. Se pedir arquivos que nunca mudam é algo **estático**, assim nasce a primeira geração de sites **dinâmicos**, cujo resultado depende do que o executável faz. O padrão chama-se **CGI** (*Common Gateway Interface*). No começo eram binários feitos em C, mas usar C para cuspir HTML é "usar canhão para matar mosca". Felizmente havia uma linguagem mais simples, nos ambientes Unix/Linux, e melhor para manipular cadeias de texto (strings): **Perl**, que se tornou a principal linguagem para CGI. Foi assim que o mundo conheceu as **expressões regulares (regex)** — coloque na sua lista obrigatória de estudos.

Depois do surgimento de alguns servidores (o do CERN, o da Netscape, entre outros), um despontou por facilidade e por ser open source: o **Apache**. Sempre ouvi que o nome vem de *a patchy server*: um "puxadinho" de remendos (*patches*) de código. Você compara duas versões de um arquivo com a ferramenta `diff`, gera um arquivo de remendo, e usa `patch` para aplicá-lo.

## O problema do copiar-e-colar e o nascimento do CSS

Uma das coisas mais irritantes da web no começo dos anos 90: para um site com dez páginas e algum layout, era preciso copiar e colar o HTML inteiro entre as páginas; para mudar o layout, abrir as dez uma a uma. A ideia original **não** era que o HTML ditasse o visual: ele foi inspirado em linguagens de marcação como o **SGML**, voltadas à estrutura de documentos (governamentais) legíveis por computador. O HTML marcava o que era cabeçalho, parágrafo, lista; **os navegadores decidiam a apresentação**, inclusive o usuário podia configurar fonte (Arial em vez de Times New Roman). Por isso as páginas do começo da web eram todas iguais: fundo cinza, fonte preta, links azuis. Havia um jeito rudimentar de forçar estilo no HTML, o atributo `style`, mas foi com o **CSS** que se separou **estilo de conteúdo**.

O CSS surgiu em ~1995–96. O Netscape já superava o antigo Mosaic, mas o **Internet Explorer** saiu na frente por implementar melhor o primeiro CSS. Surgiram páginas de teste famosas para checar compatibilidade de CSS entre navegadores (o autor deixa links na descrição). Essa briga deu início à **guerra dos navegadores** (Microsoft vs. Netscape), com cada versão tentando ser melhor visual e interativamente. Recomendo o documentário do Discovery *The True Story of the Internet* (primeiro episódio). Ao fim dos anos 90 a Netscape perdia a guerra, mudou o modelo de negócio (parou de vender o navegador) e **abriu o código-fonte, criando a Fundação Mozilla**. O **Opera** também apareceu, mostrando como redimensionar conteúdo para dispositivos móveis da época (Palm, Pocket PC, os celulares "burros" de Nokia e Siemens), e foi quando surgiu o primeiro uso de **media types** — que viraram **media queries** e só se tornaram oficiais no CSS3 (2012), com rascunhos desde ~1997. Lembre que o layout de conteúdo era especializado para papel (editoras, revistas, jornais) e agora precisava se adaptar a monitores; havia ainda outras mídias (braille, áudio para cegos). O CSS passou a perguntar ao navegador que tipo de mídia está em uso (tela de celular, tablet, computador).

Com o boom do Internet Explorer, a Microsoft passou a embutir o máximo da web no Windows. No Windows 98 vimos a integração direta no sistema operacional, incluindo **MIME types**, tecnologia surgida em e-mails para embutir binários em e-mail texto puro (*Multipurpose Internet Mail Extensions*), que determina o tipo do arquivo (`text/html`, `image/png`, `video/mpeg`) — mais avançado que as extensões do Windows. O Windows Explorer foi mesclado ao Internet Explorer, para explorar arquivos locais ou da web. Isso foi um dos estopins da acusação de **prática monopolista**: forçar o uso do Internet Explorer. A Comissão Europeia obrigou a Microsoft a deixar o fabricante escolher se pré-instalava Netscape ou Opera, mas a Microsoft argumentava que era impossível separar o IE do Windows. Foi uma controvérsia enorme na época.

## Servidores programáveis: templates, aplicações e a guerra PHP vs. ASP

Quando servidores como o Apache passaram a executar scripts que manipulam HTML antes de enviá-lo ao navegador, dava para escrever o HTML do layout **como template** e variar só o conteúdo das dez páginas; para mudar o layout bastava mudar o template. Com isso evoluímos de páginas de texto com hiperlink para algo dinâmico e visualmente mais agradável. A diferenciação passou a ser a customização gráfica; nascia a profissão de **web designer**, vinda de designers gráficos de revista tentando traduzir sua linguagem visual para a web. Foi, digo eu, a **época barroca/exuberante do design web** (muito design bizarro).

Como linguagens de servidor (Perl etc.) acessam **bancos de dados**, abre-se uma possibilidade nova: **aplicações web**, não só sites. Um formulário onde o usuário digita o cartão de crédito, enviado a um script que grava no banco — é a semente do **e-commerce**. A Microsoft não deixou a oportunidade passar: criou seu servidor web, o **IIS** (*Internet Information Services*), com tecnologias proprietárias como o **FrontPage Server Extensions** (junto com o programa FrontPage, para criar páginas dinâmicas e validações de formulário de modo simples), que só rodavam no IIS e eram interpretadas pelo IE — aumentando a pressão sobre a Netscape. Resquícios disso aparecem em produtos atuais da Microsoft, como o SharePoint.

Em paralelo ao Perl/CGI, nasceu outra forma de páginas dinâmicas: extensões embutidas **diretamente no núcleo do Apache**, cujo principal proponente foi o **PHP**: em vez de o servidor chamar um programa externo para gerar o HTML, o servidor ganhou a capacidade de interpretar lógica de programação misturada com HTML. A Microsoft seguiu lado a lado e adicionou o **ASP** em 1996 no IIS. Nasceu a **guerra server-side entre PHP e ASP**. Como consequência, ganhamos aberrações como o **ColdFusion** — o pico do mau uso do então inovador XML, usando tags não só para representar dados mas como linguagem de programação, inspirado pelo famigerado **JSP** do mundo J2EE. Isso coincide com a evolução do Java no servidor e com outra categoria: os **servidores de aplicação**. Um servidor de aplicação é um servidor web, mas nem todo servidor web (como Apache ou Nginx hoje) é de aplicação: servidores web servem páginas HTML; servidores de aplicação **executam programas que cospem HTML**.

Essa época coincide com o IPO da Netscape (início da **bolha da internet**, meio ao fim dos anos 90), com a entrada de programadores mais experientes que meros designers de HTML e com tecnologias para tráfego seguro (**SSL** da Netscape). Nascem as primeiras aplicações web: **CMS** (*content management systems*), como o monstruoso Vignette que os portais de conteúdo usavam, e versões open source como PHP-Nuke e Mambo (que inspirou Drupal, Joomla), Zope em Python (que originou o Plone) e, no começo dos anos 2000, o **WordPress**, que ajudou a iniciar a era dos blogs.

## CSS2, DHTML, AJAX e o Gmail

Quando ficou claro que dava para programar aplicações interativas, controlar o visual ficou cada vez mais importante: evolução do **CSS2**, que inaugurou a época das **web fonts** e moveu os layouts de **tabelas** para **elementos flutuantes / layout fluido**. Nasceram também duas tecnologias fundamentais da web de hoje: o **DHTML** (HTML dinâmico, com HTML 4) e o **AJAX** (*Asynchronous JavaScript and XML*; o autor atribui a inauguração à Mozilla — [external] o `XMLHttpRequest` nasceu na Microsoft, no IE5), cujo principal garoto-propaganda foi o **Gmail**, desenvolvido a partir de 2001 e lançado em **1º de abril de 2004** (também inaugurando a era dos memes de 1º de abril). O Gmail foi a personificação do que **Bill Gates temia nos anos 90**: que os navegadores se tornassem substitutos dos sistemas operacionais na função de executar programas. Ele previu corretamente: sem padrões proprietários, você não segura os usuários do Windows, porque eles podem rodar o mesmo programa no navegador em qualquer sistema (Mac, Linux). O Gmail foi provavelmente a primeira aplicação web que substituiu com sucesso um dos programas nativos mais importantes — o **cliente de e-mail** (Outlook) — e isso ameaçava tudo, incluindo o monopólio do Office.

**Estado do front end em 2004:** HTML até a versão 4 (DHTML, AJAX); surge o **XML** para estruturar qualquer tipo de dado (e o **XHTML** como caso especial: HTML estrutura conteúdo de texto, XML estrutura dados como cadastros); **CSS 2.1** (web fonts, internacionalização, posicionamento relativo/absoluto, elementos se ajustando ao tamanho da tela, em oposição ao comprimento fixo de tela dos anos 90, com muito recorte de imagens dentro de tabelas porque o CSS não era poderoso). CSS é uma linguagem **declarativa**: declaramos regras visuais aplicadas ao HTML, em **cascata** (regras com especificidade). **Tenha sempre em mente a estrutura de árvore**: HTML são árvores de elementos, CSS são árvores de atributos de estilo, sites são árvores de páginas linkando umas às outras. Quase tudo na web é baseado em hierarquias.

## Frameworks e Rails

De sites de conteúdo hipertexto passamos a gerenciadores de conteúdo, e-commerce e, com Gmail e redes sociais (Orkut, MySpace, Friendster), **aplicativos web**. Em paralelo, na era Java do começo dos anos 2000, popularizou-se o conceito de **frameworks**: mais que linguagens, fornecem estrutura pré-definida (segurança, acesso a dados, autenticação e autorização granulares, padrões visuais) e determinam **onde colocar cada tipo de código**. Antes, cada aplicativo PHP fazia tudo do zero. No PHP surgiram frameworks inspirados no J2EE, e finalmente chegou a era do **Ruby on Rails** (fim de 2004), com o lendário demo "blog em 15 minutos" que David Heinemeier Hansson gravou, e apresentado no evento Rails de 2005 (o autor cita o evento no Brasil), inaugurando a era dos frameworks ágeis (o Manifesto Ágil é de 2001).

Por causa do Rails surgiu a primeira geração de **frameworks/micro-frameworks JavaScript e CSS**. Até então, escrever HTML, CSS e JavaScript era trabalhoso e **não funcionava igual em todos os navegadores** (época do IE6, Windows XP, Netscape 7). Alguém pensou: por que não unificar? Surge a primeira geração de bibliotecas do lado do navegador: Dojo (inferido), **jQuery** e as que o Rails popularizou, **Prototype** e **script.aculo.us**, que popularizaram interações como **drag and drop** (como arrastar e-mails no inbox do Gmail), evitando código específico para IE ou Netscape.

## 2007: o iPhone e o fim dos plugins

Em julho de 2007, o **primeiro iPhone** muda a usabilidade e o design. Seu navegador Safari evolui do **Konqueror/KHTML** do KDE (Linux), que se tornaria o **WebKit**. A tela do celular era bem menor que a de desktop: em 2007 o comum eram monitores de 1024×768, enquanto o iPhone tinha **320×480**.

Antes, nos anos 90, havia outra forma de tomar a dianteira sem HTML/CSS/JS: empresas criaram **plugins proprietários**. A Microsoft fez componentes (FrontPage, ASP). A Sun criou o Java e queria **colocar Java em tudo**, inclusive no navegador. Para evitar risco de segurança, criou-se o conceito de **sandbox**: um container que executa código com baixos privilégios (sem acesso a arquivos ou rede). Nasceram os **applets** (quem não lembra do applet de demonstração da água se mexendo?). A Microsoft criou o **ActiveX**, equivalente ao applet, mas com C++, VB6 etc. Felizmente applets Java e ActiveX já não existem. A Macromedia fez seu plugin **Flash**: ilustrações vetoriais com curvas de Bézier (como no CorelDRAW/Illustrator), traços de qualidade e tamanho muito menor que bitmap (JPEG/GIF), **linha do tempo** para animar e uma linguagem simples, o **ActionScript**, permitindo coisas interativas como joguinhos. Todo mundo jogou algo em Flash no começo dos anos 2000.

Comparação de potência: o processador de um iPhone de 2019 (A12 Bionic) é quase tão potente quanto um Intel Core de MacBook Pro; o do iPhone original (2007) era um ARM11 de 412 MHz com **128 MB de RAM**, bateria de ~1.400 mAh e sem teclado nem mouse — rodar Flash era um exercício de futilidade. Os primeiros Android quiseram se destacar rodando Flash, mas provaram que ele deixava o celular extremamente lento e esgotava a bateria. O Flash já tinha má reputação por bugs e graves buracos de segurança; em desktop com CPUs fortes dava para aguentar, mas em smartphones não. A **Apple se recusou a rodar Flash** e o demonizou na carta aberta de Steve Jobs, selando o fim.

Só que, desde 2005, a única forma decente de ver vídeos do YouTube era o plugin Flash (ou o Silverlight, evolução do ActiveX, que também não durou). A Apple ajudou a evoluir o HTML para **playback de vídeo acelerado por hardware** e popularizou o envelope **MP4** com compressão **H.264**, nascendo a tag `<video>`. Somado ao fim do Flash, aumentou a pressão por animações aceleradas por GPU: surgem coisas como `transform` e transições controladas por CSS, e WebGL. Com a revolução dos smartphones, a queda da Sun (adquirida pela Oracle, que pôs um ponto final nos applets) e o desinteresse da Microsoft pós-julgamento antitruste (que desacelerou o IE e o Silverlight), o W3C e seu consórcio foram forçados a acelerar a evolução para **HTML5 e CSS3**, só oficializados em **2014**, e antes disso, desde o **Google Chrome (2008)**, todos os navegadores implementavam uma funcionalidade por vez.

## 2008–2015: transição caótica e meta-linguagens

De 2008 a 2015 houve um período chato de transição: HTML, CSS e JavaScript mudavam o tempo todo em cada versão de cada navegador, era impossível fazer um site que funcionasse em todos os navegadores e dispositivos. Por isso surgiram **meta-linguagens** para nos blindar: o **jQuery** deixou de ser opcional e virou necessidade para JavaScript; com o fim do Flash, o JavaScript voltou a ser a única alternativa viável para animação e interação — uma linguagem ruim, sem evolução significativa desde o início dos anos 2000. Surgiu a gambiarra dos **transpilers**: linguagens que não compilam para instrução de máquina real ou virtual, mas **traduzem uma linguagem em outra**.

O mundo Ruby on Rails ajudou de novo: o **Sass** (SCSS) é um dialeto de CSS que permite estruturar melhor o CSS (reusar código, esconder detalhes específicos de navegador). O Twitter criou sua versão, o **Less**; competiram por anos, mas o Sass é superior hoje. Em 2009, Jeremy Ashkenas escreveu o **CoffeeScript**, uma nova linguagem cuja compilação gera JavaScript, trazendo conceitos de Ruby e Python — mais agradável de trabalhar. Hoje muita gente demoniza o CoffeeScript pela sintaxe agressiva e pouco ortodoxa, mas dele saíram conceitos como **interpolação de strings**, melhor controle de escopo (variáveis), **arrow functions** (sintaxe `=>` para funções anônimas) etc., incorporados ao **JavaScript ES6, que só saiu em 2015**, tornando o CoffeeScript obsoleto.

Além de matar o Flash, os smartphones com telas **verticais** e resoluções diferentes exigiram estilos que se adaptassem ao formato da tela; com a migração das **tabelas** para elementos flutuantes com espaçamento relativo e o CSS3, nasceu o **design responsivo**, o layout que se adapta ao dispositivo. Com a interação via toque nasceu uma nova classe de pesquisa, o hoje chamado **UX / usabilidade**: até então o normal era teclado e mouse; como criar telas que só usam o dedo? Hoje é problema resolvido, mas em 2007–2015 foi assunto de muita discussão.

O iPhone trouxe, além da tecnologia, o **DNA de design** da Apple. Se o fim dos anos 90 foi a época barroca do design web, a Apple trouxe a linguagem **Bauhaus / minimalismo**: espaços em branco, linhas simples, contra o escândalo de cores bregas e tudo desalinhado dos MySpace da vida. Em cima dessa linguagem, as empresas pararam de reinventar a roda e passaram a criar **bibliotecas de estilo reutilizáveis**, os **frameworks de CSS**, escritos em linguagens como Sass/Less, o mais famoso o **Twitter Bootstrap**. Por isso muitos sites parecem feitos pelo mesmo designer: todo mundo usa Bootstrap. Criaram-se elementos novos (menu "hambúrguer", modais, *scroll* etc.).

## Gerenciadores de pacotes, minificação e pipelines

Com tantos novos arquivos de JavaScript e CSS, surgiu outra necessidade: não era mais só um arquivo de CSS e um HTML pronto; passamos a reusar dezenas de bibliotecas (Google Analytics, frameworks de CSS gigantes, etc.). Primeiro precisávamos **baixar** todos esses assets e bibliotecas sem ir de site em site, clicando em download e descomprimindo zips manualmente. No mundo Perl já havia o **CPAN**; no Ruby, depois de várias tentativas, consolidou-se o **Bundler**, que não só baixa mas gerencia as **versões corretas**; no JavaScript as coisas começaram devagar com o **npm**, que só ficou realmente usável quando concorrentes (Yarn) tentaram tomar seu lugar; o npm se tornou o padrão de fato de gerenciamento de dependências no lado do desenvolvedor (o **Bower** também existiu).

Mas isso não basta: o servidor web cospe HTML e todos esses assets para o navegador; quanto mais e maiores os arquivos, mais lento. Isso ficou óbvio nos primeiros smartphones: em 2009 o normal ainda era 2G, poucos 3G (hoje 4G e já indo para 5G). Como otimizar? Assets são texto; nós, programadores, escrevemos código com tabulação, espaços e nomes grandes e descritivos para outro programador editar. O navegador não se importa com espaço em branco nem nomes descritivos; isso ocupa espaço desnecessário. Quanto mais arquivos separados, mais lento; então **junte vários arquivos em um só**, filtre espaços em branco, reduza nomes de variáveis/funções ao menor tamanho. Esse é o conceito de **minificação** (*minify*): textos legíveis em textos menores e horrorosos, que o navegador lê.

Com tantas etapas (transpilar Sass → CSS, CoffeeScript → ES5, que era o mais usado então, minificar, concatenar) para chegar nos arquivos finais de HTML, CSS e JS otimizados, temos o **pipeline de processamento de assets**, que o Ruby on Rails chamou de **asset pipeline** (onde o conceito nasceu). No mundo JavaScript surgiram ferramentas similares (Grunt/Gulp) e hoje o npm somado ao **Babel** e ao **Webpack** faz esse tipo de coisa; por isso todo framework novo que se preza tem integração com **Webpack** para ter esse pipeline. Isso ficou um pouco menos necessário desde o **HTTP/2** (assunto para outro dia).

## SPAs, frameworks de componentes e híbridos

Evoluindo sobre a herança do Gmail, só AJAX não era mais suficiente: passamos a tirar a lógica dos servidores de aplicação e a transferir o **controle do estado da aplicação para perto da tela**, e assim surgem os **frameworks JavaScript** (MVC / componentes). Em vez de controlar cada elemento individualmente via JavaScript e controlar estilos globais com CSS, organizamos a tela em coisas maiores: no Spotify, em vez de botões e listas, falamos em **playlist, menu do usuário, dashboard de playback, lista de resultados de busca** — grandes **componentes** que interagem entre si, cada um com representação gráfica que depende de um **estado** (no playback: tocando, pausado, faixa ativa ou não). Para criar componentes e gerenciar estado no cliente, aproveitando tecnologias do HTML5 como **Web Storage** (guardar estado no navegador), surgem **Backbone, Ember, React (com Redux), Vue.js**; e o conceito de uma **única página** que carrega toda a aplicação (JavaScript, assets, CSS, imagens), sem trocar de página entre estados: usa AJAX por baixo e muda tudo na mesma página — as **SPAs (Single Page Applications)**. Isso veio com aplicações complexas em interação e estado: Google Docs, Slack, Spotify.

A Apple, na dianteira por causa do iCloud, tinha o **SproutCore**, de onde veio a semente do **Ember** (que saiu da comunidade Rails, por isso lembra a estrutura do Rails). O Google tinha o **GWT** (muito usado no mundo Java para apps como o Gmail), depois criou o **AngularJS** e depois o **Polymer**, que não deu muito certo em adoção. Com o crescimento do Facebook e a necessidade de apps como o Messenger surgiu o **React**, que torna mais veloz o desenho da parte da tela cujo estado mudou usando o **Virtual DOM**: em vez de redesenhar explicitamente um elemento (mudar a cor de um botão para vermelho), só mudamos o **estado** do botão e deixamos o Virtual DOM redesenhar o que precisa, evitando redesenhar o que não precisa e otimizando a velocidade total. Tentando competir e evoluir a partir da experiência do Ember e do React, no mundo open source surgiu o **Vue.js**, que ganhou momentum por ser incluído como padrão no **Laravel** (PHP).

Hoje, com o JavaScript ES6, a dominância do Chrome, a decadência do IE, processadores multi-core mais rápidos e eficientes nos smartphones e RAM mais barata (6, 8 GB ou mais), surge uma nova classe de aplicativos: os **híbridos**, apps de desktop ou mobile com uma estrutura nativa que se liga ao hardware (câmera, touch, áudio), mas controlados por uma **fina camada de JavaScript e tecnologias web** (HTML5, CSS3). Dá para usar a mesma estrutura para desktop e mobile: Spotify, Slack, editores como Atom e **Visual Studio Code**. Surgem frameworks híbridos como o **Electron** (encapsula tecnologias do Chrome e abre como app nativo) e o **React Native** (desenvolver app iOS/Android como se fosse um site em React).

## Fechamento: como estudar

Eu sei que pincelei por cima dezenas de assuntos e mais de 25 anos de história. Sinto que nasci na hora certa: vi cada evento acontecer em tempo real, aprendi cada tecnologia à medida que apareceu. Algumas já morreram: ASP clássico, Flash, Silverlight, ActiveX, applets Java, CoffeeScript, GWT; ao mesmo tempo apareceram HTML5, CSS3, JavaScript ES6 e as ferramentas por cima. Espero que a linha do tempo dê noção de onde cada coisa se encaixa; recomendo reassistir ao episódio de tempos em tempos.

**Sempre que tiver dúvida sobre uma tecnologia, comece do começo: pesquise sua história.** A história diz por que ela existe e que problemas foi desenhada para resolver. Perguntas-guia: ela ainda resolve esse problema da melhor forma? Já surgiram substitutos? Ainda vale aprender ou há coisa melhor? Por onde anda o autor original ou a empresa que a patrocinou? Se fiz meu trabalho direito, você começou o episódio com dúvidas e termina com mais dúvidas ainda — e esse é o objetivo. **Se você tem poucas perguntas, não está se esforçando o suficiente; faça a pergunta errada e receberá a resposta errada.** Coloque as tecnologias na linha do tempo, veja quais problemas resolvem, encontre problemas para resolver e vá aprendendo na tentativa e erro.

Exemplo prático: abra projetos open source no GitHub (quase tudo em inglês). Se você já entendeu para que serve o Angular, procure um tutorial; ao ver arquivos `.scss`, você agora sabe que é Sass e que deve haver um pipeline com Webpack — procure tutoriais de Sass e Webpack. Ao rodar, você já sabe a diferença entre servidor web e servidor de aplicação. E se levou a sério o episódio anterior, você está estudando distribuições Linux: procure um tutorial de como instalar, configurar e subir um Nginx, por exemplo.

O objetivo de hoje foi colocar as tecnologias de front end dentro da história. **Semana que vem** quero fazer a mesma coisa com tecnologias de **back end**, e na seguinte, finalmente, um pouco sobre DevOps. Não sou o melhor programador de front end, então mandem dúvidas nos comentários para todo mundo ajudar a responder. Se curtiram, deixem o like, compartilhem, assinem o canal e ativem o sininho.
