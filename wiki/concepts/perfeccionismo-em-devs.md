# Perfeccionismo em Devs

Padrão comportamental onde o dev adia o ship porque o produto "ainda não está pronto" — quando na realidade nunca ficará. Funciona como mecanismo de autodefesa (self-handicapping): se o produto nunca sai, nunca pode ser julgado ou falhar.

## Manifestações Comuns

- Feature core pronta, mas preso em refactors intermináveis
- "Vou melhorar essa UI antes de mostrar para alguém"
- "Talvez reescrever em TypeScript resolva o problema"
- "Na verdade, devo começar do zero com uma arquitetura melhor"
- Preocupação excessiva com o que "especialistas da internet" vão achar

## Self-Handicapping

O perfeccionismo é frequentemente **proteção psicológica**, não busca de qualidade:
- Se o produto nunca sai → nunca recebe feedback negativo
- Se o produto é "imperfeito" → qualquer crítica pode ser atribuída à incompletude, não à ideia

## Distinção: Qualidade vs. Perfeccionismo

| Qualidade | Perfeccionismo |
|---|---|
| Código funciona e é mantível | Reescrever código que já funciona |
| Testes cobrem os casos críticos | 100% de cobertura antes de qualquer ship |
| UX clara para o usuário | Pixel-perfect antes do primeiro usuário |

## Mitigação

- Definir critérios de "done" antes de começar (não durante)
- **[[concepts/mvp]]**: "bom o suficiente para shippar" como meta explícita
- Separar "ship" de "perfeito" — iterar após feedback real é mais eficiente que polir no vácuo
