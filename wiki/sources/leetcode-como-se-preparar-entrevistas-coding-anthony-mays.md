# LeetCode: você provavelmente está se preparando errado para entrevistas de coding

## TL;DR

Vídeo em inglês (traduzido para português nesta ingestão) de Anthony D. Mays, ex-entrevistador técnico em big techs, explicando pela perspectiva do entrevistador por que a maioria das pessoas se prepara errado para entrevistas estilo [[wiki/concepts/entrevista-tecnica-coding|LeetCode]]: memorizar problemas prontos em vez de padrões, evitar ficar travado a todo custo, e correr para a primeira solução sem refletir. A tese central é que a entrevista mede processo de raciocínio e comunicação, não só a resposta certa — e que fazer perguntas de esclarecimento é trabalho do candidato, não algo que o entrevistador antecipa.

## Key Claims

- **Entrevistadores evitam usar problemas prontos de plataformas como o LeetCode** porque um candidato pode já ter memorizado a solução exata — isso não prova capacidade de resolver problemas novos. → [[wiki/concepts/entrevista-tecnica-coding]]
- **A recomendação é memorizar o padrão, não o problema** — é possível fazer centenas de problemas no LeetCode e continuar sem evoluir a capacidade real de resolver problemas, se o foco for memorização em vez de reconhecimento de padrão. → [[wiki/concepts/reconhecimento-de-padroes]]
- **Resposta certa não é suficiente**: o entrevistador quer entender como o candidato pensa e se comunica, principalmente quando trava. Se o candidato já sabe a resposta de cara, o entrevistador aumenta a dificuldade ou troca de pergunta para gerar sinal real.
- **Ficar travado é esperado e faz parte do processo avaliado** — evitar isso a todo custo é sinal de despreparo. A maioria das pessoas não tem memória fotográfica, e não é isso que está sendo medido. → [[wiki/concepts/aprendizado-por-luta]]
- **Diferença central entre praticar sozinho e ser entrevistado**: no LeetCode o enunciado, exemplos e dicas vêm completos de uma vez; numa entrevista real o candidato precisa saber pedir a informação que falta — o entrevistador não antecipa esse trabalho.
- **Sinal de alerta clássico de reprovação**: começar a digitar código imediatamente após ouvir o problema, sem perguntas de esclarecimento — normalmente produz solução incompleta.
- **Estudar algoritmos, estruturas de dados e Big O serve, na prática de entrevista, para saber que perguntas fazer** e filtrar abordagens que não se aplicam (ex.: perguntar se o input já está ordenado descarta algoritmos de ordenação do conjunto de opções). → [[wiki/concepts/big-o]]
- **É válido perguntar ao entrevistador qual solução ele prefere**, quando há mais de uma opção viável — evita gastar tempo implementando algo que os dois já sabem que não é ideal.
- **É literalmente o trabalho do entrevistador ajudar o candidato** — tratá-lo como adversário e evitar perguntas prejudica só quem está sendo entrevistado.

## Conexão com a perspectiva do entrevistador/contratante

O ponto de vista desta fonte é o do candidato se preparando, mas complementa a perspectiva de quem conduz a entrevista já documentada na skill `tech-mentor-leadership` (`references/leadership/engineering-hiring.md`): lá, "Leetcode hard obrigatório" é listado como anti-padrão de processo seletivo (filtra bons engenheiros que não treinaram competição, não prediz performance real), e "fazer perguntas de clarificação antes de desenhar" aparece como sinal positivo explícito em entrevistas de system design. As duas fontes se reforçam: o problema não é o formato em si, é tratá-lo como teste de memorização em vez de processo de raciocínio observável — visão compartilhada tanto por quem prepara candidatos quanto por quem estrutura o processo de contratação.
