# Escopo Bem Definido em Projetos: o Valor Está no Processo, Não no Resultado

## TL;DR

[[wiki/entities/lord-lorehub|Lord]] (canal/comunidade LoreHub) desmonta a crença de que projeto pessoal precisa ser "revolucionário" para valer a pena: o valor real está no processo de construção (o que se aprende), não no resultado final ou na ambição da ideia. Prescreve um método tático já usado desde a criação do próprio LoreHub — abrir um `.md`, listar o que precisa funcionar na v1, e usar **user stories** ("como usuário, quero...") para quebrar uma ideia vaga em pedaços terminináveis. Introduz o conceito complementar de **engineering stories** ("como dev, quero...") para requisitos invisíveis ao usuário (testes, ausência de duplicação). Fecha respondendo a uma pergunta de espectador sobre medo de aplicar para vagas de estágio: a sensação de "nunca estar pronto" é permanente, então a recomendação é aplicar apesar do medo.

## Key Claims

| Claim | Evidência |
|---|---|
| O valor de um projeto pessoal está no processo de construí-lo (aprendizado), não em ele ser usado pelo mundo | Exemplo do app de previsão do tempo: não é para competir com o "melhor app já feito", é para aprender a consumir API, renderizar dados dinamicamente e tratar erros |
| A crença de que só vale a pena construir algo "bilionário"/revolucionário é uma armadilha que trava o início de projetos | Relato em primeira pessoa: comparar qualquer projeto normal a "criar o próximo Facebook" tornava tudo parecer perda de tempo |
| "Não achar nenhum projeto interessante" é frequentemente desculpa, não critério real de escolha | Autocrítica explícita ("sommelier de projetos"); admite que alguns projetos necessários simplesmente não são interessantes |
| Confiança de que "sei construir algo" só porque parece simples na teoria é diferente de saber construir na prática | Frase: "teoria está muito, muito longe da prática" |
| Escrever um checklist de requisitos da v1 num arquivo `.md` antes de codar é o método tático recomendado, usado desde a criação do próprio projeto do autor (LoreHub) | Exemplo do app de clima reduzido a duas etapas: (1) buscar dados de uma API, (2) mostrar os dados — "funcionou, pronto" |
| User stories ("como usuário, quero [ação] para [benefício]") são a ferramenta recomendada para descobrir os requisitos do checklist | Exemplo: "como usuário, eu quero consultar o clima atual" / "como usuário, eu quero visualizar os dados" |
| "Engineering stories" ("como dev, quero...") cobrem requisitos que o usuário não vê e não valoriza diretamente | Exemplos dados: "como dev, eu quero testes unitários" / "como dev, eu quero evitar código duplicado" |
| A sensação de nunca estar completamente preparado para aplicar a uma vaga (de estágio) é permanente, não um estágio a ser superado antes de agir | Resposta direta à pergunta do espectador: "você provavelmente nunca vai se sentir completamente preparado [...] esperar se sentir pronto pode fazer você esperar para sempre" |

## Conceitos

- [[wiki/concepts/necessidade-como-gatilho-de-aprendizado]] — mesma lógica ("aprender por necessidade/lacuna", não por ambição ou hype) aplicada especificamente à escolha de projetos pessoais, não apenas a tópicos de estudo
- [[wiki/concepts/checklist-primeiro-dia-projeto]] — reforça, de fonte independente, o método do checklist `.md` de requisitos da v1 antes de codar
- [[wiki/concepts/user-stories]] — aplicação do formato canônico fora de contexto de time ágil formal: uso solo, para decompor uma ideia vaga em unidades terminináveis
- [[wiki/concepts/mvp]] — o app de clima de duas etapas é um MVP mínimo de aprendizado (não de mercado): "funcionou, pronto" como critério de conclusão da v1
- [[wiki/concepts/sindrome-do-impostor]] — nova variante: medo de aplicar para uma vaga (não medo pós-contratação) por nunca se sentir "pronto o suficiente"
- [[wiki/concepts/persistencia-em-processo-seletivo]] — conceito irmão cronologicamente anterior: esta fonte cobre o momento de *aplicar apesar do medo*, aquele cobre o momento de *persistir depois de reprovado*
