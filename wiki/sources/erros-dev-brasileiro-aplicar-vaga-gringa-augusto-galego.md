# Erros de Devs Brasileiros ao Aplicar para Vagas na Gringa (Augusto Galego)

## TL;DR

[[wiki/entities/augusto-galego]] lista sete erros de quem aplica para empresas estrangeiras: (1) achar que precisa de inglês perfeito ou, no extremo oposto, ignorar o [[wiki/concepts/ingles-tecnico-suficiente-vs-perfeito|inglês técnico necessário]]; (2) respostas secas, sem [[wiki/concepts/storytelling-em-entrevista]]; (3) não treinar LeetCode e System Design, que as Big Techs voltaram a cobrar presencialmente; (4) não [[wiki/concepts/explicar-o-porque-das-decisoes|explicar o porquê]] das decisões; (5) ficar em silêncio em vez de [[wiki/concepts/pensar-em-voz-alta-na-entrevista|pensar em voz alta]]; (6) chegar sem [[wiki/concepts/pesquisar-a-empresa-antes-da-entrevista|pesquisar a empresa]]. Tese de fecho: o processo é, em essência, o mesmo do Brasil ([[wiki/concepts/vaga-internacional-sem-mistica]]).

## Key Claims

| Claim | Evidência (no vídeo) | Confiança |
|---|---|---|
| Inglês perfeito não é exigido; muitos colegas gringos têm inglês "bom", com lacunas em termos técnicos | Italianos/franceses/espanhóis não sabem nomear símbolos (`\`, `/`, `:`); o próprio autor hesita | Média: anedota pessoal |
| Mesmo assim, "cara de pau" não passa; o inglês precisa ser adequado a *conversar sobre software*, não a "viver em inglês" | Vocabulário (*back pressure, queues, modules*) pesa mais que tempos verbais; rejeita a regra "B1–B2" | Média: opinião; contrasta com a régua B1–B2 que o próprio autor cita como convenção |
| Respostas diretas demais fazem o candidato perder; história com desafio técnico + impacto + medição convence | Exemplos "foi bom, usei Java e Postgres" e "migração Java 8→9" respondem sem mostrar competência | Média: sem dados de contratação |
| Ensaiar a história (sem decorar) combate o nervosismo | Explicar o projeto ao espelho, ao bichinho de pelúcia ou à mãe | Média: conselho prático, não testado |
| Big Techs voltaram a cobrar LeetCode/System Design **presencial** para impedir IA em entrevista remota | Empresas ainda não adaptaram o processo e não usam IA bem para contratar | Baixa/média: afirmação do autor `[external não verificado]` |
| Para LeetCode: ~10 exercícios do mesmo padrão; se travar, ler a solução, reescrever e seguir | Começar por array → two pointer → sliding window | Média: coerente com [[wiki/sources/como-ficar-bom-em-leetcode]] |
| Para System Design: estudar building blocks *antes* de praticar | Lista: banco, load balancer, API gateway, lambda, networking, client-server, micro/monolito, serverless | Média |
| Contar o *porquê/como* das decisões (monólito → microsserviços, login com Google) demonstra senioridade | Perguntas "por que não escalar o servidor? quem decidiu?" | Média |
| Silêncio ou balbucio de código impede o entrevistador de medir o raciocínio | Exemplo do Fibonacci; entrevistador é colaborativo | Alta: alinhada a várias fontes da wiki |
| 15 minutos de pesquisa (com Claude Code/GPT) bastam para chegar preparado | Pedir resumo e perguntas ao RH; perguntar sobre problemas do nicho | Média |
| Empresa gringa não tem nada de mágico | ~6 anos no Brasil e ~5 em empresas de fora; "salvo o idioma, talvez não notasse diferença" | Baixa/média: visão de uma só pessoa (declarado) |

## Perguntas em aberto

- A volta das entrevistas presenciais de LeetCode/System Design nas Big Techs é generalizada? Sem dado na fonte `[external não verificado]`.
- Tensão: "decorar a resolução" ([[wiki/sources/como-ficar-bom-em-leetcode]] e este vídeo) vs. "memorize o padrão, não o problema" ([[wiki/sources/leetcode-como-se-preparar-entrevistas-coding-anthony-mays]]). Provável convergência: decorar *depois* do timebox, para extrair o padrão, não para repetir a resposta.
- O autor aceita a régua "B1–B2" como convenção mas a considera pouco informativa; falta critério operacional alternativo (ex.: teste de explicar um design em inglês).
